# How many agents to launch (and what isn't parallelized)

The rule that summarizes everything else:

> **Parallelize LOOKING. Serialize TOUCHING.**

Looking at material — photos, frame strips, ring sheets, transcriptions — is where the real work is and
where N agents give you almost N times the throughput. Touching things — a desktop app, the photo
library, the same output file — doesn't parallelize: it collides.

## How many context agents

| Files to catalog | Parallel agents | How it splits |
|---|---|---|
| under 200 | **3** | by day or by place |
| 200 to 1000 | **6** (8 if there are more than 10 days) | one agent per day, or per batch of ~150 files |
| over 1000 | **10** (practical cap) | cheap sift first; then one agent per batch of ~150 of what survived |

On top of that, always:

- **1 agent per 360 clip.** A 20 s equirectangular clip yields three or four different framings and needs
  its own ring sheets. Mixing it into that day's photo batch makes the agent pull a single framing and
  miss the rest.
- **1 trend agent**, with web search, running in parallel with everything else. It doesn't depend on the
  catalog and the catalog doesn't depend on it, so it has no reason to wait its turn.
- **2 builder agents per concept**, with the variants split between them.
- **1 reviewer agent per concept**, different from the builders.

Never more agents than units of material: an agent with half a day of photos has nothing to compare
against and repeats what the one next to it already said.

### The two caps that actually bind

1. **The Workflow tool's cap: `min(16, CPUs − 2)` simultaneous agents.** You can hand `pipeline()` 40
   batches without a problem; the surplus waits its turn. What you can't do is *force* more concurrency
   than exists.
2. **The machine.** Past ~10 active agents that also invoke `ffmpeg`, renders start taking minutes and
   everything feels stuck. `ffmpeg` already uses several cores on its own: four simultaneous renders don't
   take a quarter of the time, they take almost as long as running them in series and they leave the
   machine useless for anything else.

## What parallelizes well

| Work | Unit | Why it scales |
|---|---|---|
| Looking at photos | a day, or a batch of ~150 | independent of each other; the agent only reads and describes |
| Watching videos | a batch of ~4 videos | each video is ~15 tool calls; past 4-5 the agent runs out of context and starts describing from memory |
| Watching 360 clips | one clip | each clip needs its own sheets and its own keys |
| Researching trends | 1 agent | depends on nothing, starts first and gets collected at the end |
| Building variants | 2 per concept | two independent agents **diverge**; one agent with four variants copies itself |
| Reviewing | 1 per concept | it has to see every variant together, so it's one — but concepts get reviewed in parallel with each other |

## What is NOT parallelized

- **Driving a desktop app by clicks.** The CapCut narrator voice
  (`skills/voices/scripts/capcut_voice.py`, **macOS only**) is generated by moving a single window: its
  position is pinned, clicks land on coordinates and the file is awaited. Two agents doing it at once
  steal focus from each other and the clicks land in the other's window. **It runs in series, one agent,
  one batch.** The app also gets tired: a project with ~100 generations on it stops writing audio with no
  error at all; you have to create a new project and carry on. If that happens, deliver the video without
  voice and the `voice-script.txt` alongside it.
- **Exporting from the system photo library.** On macOS the iCloud download of originals is serialized by
  the OS itself; several processes at once don't download faster, they just fail more. Do the export
  **once, up front**, and leave the files in `workspace/material/` so the agents only read from disk.
- **Heavy renders.** See above: `ffmpeg` is already parallel internally.
- **A concept's shared work.** The 9:16 crops, the pre-renders and the music bed are done **once** in
  `concepts/<id>/common/`, not inside each builder. When each agent did it on its own, one used the raw
  30 s song preview and the last 6 seconds of its video came out silent without anything failing.
- **Writing the same file.** One agent, one batch, one output file (`catalog-<batch>.json`). Two agents
  over the same JSON overwrite each other and the error shows up days later, when half a day is missing.
- **Deciding.** The concepts, the shot order and what gets delivered are not handed out: you decide those
  by reading what the agents returned. A committee of agents produces four videos that look alike.

## Always write to disk

A catalog run with 10 agents is 20-40 minutes of work. If it gets interrupted — the user cancels, an
agent crashes, the battery dies — **whatever isn't on disk is lost**.

- **Every agent writes its result BEFORE answering.** The prompts in `workflows/catalog.js` require it:
  `workspace/catalog/catalog-<batch>.json`. And if that file already exists and is complete, the agent
  reads it and returns it instead of looking at everything again. The second run costs almost nothing.
- **`workspace/` is rebuildable; `deliveries/` is not touched.** Every variant leaves a `build.py` that
  regenerates its spec and its pre-renders from scratch. Never leave a `spec.json` pointing at a temporary
  you already deleted: once the temporaries are cleaned up, that spec is irreproducible.
- **Resuming the whole run:** the Workflow tool returns a `runId`. With
  `Workflow({ scriptPath, resumeFromRunId: "<runId>" })` the unchanged prefix comes back from cache
  instantly and only the first modified call onward gets re-executed. Same script and same `args` = all
  cached.
- **No silent shortcuts.** If a run reduces coverage (two batches crashed, the verification got skipped,
  300 files were left out), say it with `log()` and in the final summary. A reduction that isn't announced
  reads as "I reviewed everything".

## How this looks in the workflows

- **`workflows/catalog.js`** uses `pipeline()`, not `parallel()`: each batch moves to its verification as
  soon as it finishes, without waiting for the others. The only barrier is at the end, to merge and
  deduplicate, which is the only thing that needs every batch at once. The trend agent is launched
  **without `await`** at the start and collected at the end, so it runs in the background throughout the
  catalog.
- **`workflows/build.js`** also runs the concepts through `pipeline()`. The barrier that genuinely is
  needed — a concept's two builders have to finish before its reviewer can compare them — is solved with a
  `parallel()` **inside** the stage, so it only blocks that concept. The fix stage only spends agents if
  the reviewer found something blocking.

## Signs you launched too many agents

- Two batches return the same description in different words → the batches were too small.
- An agent returns generic moments ("nice landscape", "him smiling") → it didn't look; it had too much
  material or too little context.
- Renders that took 40 s now take 4 minutes → there's too much `ffmpeg` competing. Reduce the wave.
- The catalog has 600 moments → nobody sifted. Fewer agents and harder drop rules pay off more than more
  agents.
